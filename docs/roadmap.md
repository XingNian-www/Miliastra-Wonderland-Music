# 后续发展路线

> 本文是项目维护建议，不是已完成清单、发布日期承诺或线上质量报告。项目结构见 [项目导览](project-overview.md)。

## 1. 核心判断

项目已经覆盖点歌、多个音乐源、登录、OCR、自动操作、娱乐玩法和 Web 管理，下一阶段最有价值的不是继续增加菜单，而是让已有能力稳定、可解释、易部署。

建议定位为：**面向千星场景、可长期运行的音乐与互动助手**。

- 主线：可靠点歌、播放、队列、歌词和账号维护。
- 支撑：可回归的画面识别、可恢复的任务执行、清晰的状态与诊断。
- 扩展：多人娱乐、房间运营、受约束的 AI 辅助。
- 暂不转向：通用桌面 Agent、云端多租户平台、跨平台重写。

这是基于现有结构的工程方向建议；没有用户访谈、活跃度、故障率或转化数据支撑商业优先级。新增玩法和产品能力应先从实际房主/维护者反馈中验证需求。

## 2. 现状证据与优先级

| 优先级 | 已观察到的事实 | 判断/建议 |
| --- | --- | --- |
| P0 | 主发布工作流以编译、打包为主，无通用 fmt/clippy/test 和 PR 触发；OpenVINO 有专门 fixture 测试 | 把现有回归测试接入常规变更流程，不是从零另造测试体系 |
| P0 | 点歌榜未提交变更跨播放确认、持久化、HTTP 和页面 | 先验证并独立收口这批变更，再叠加重构 |
| P0 | 本地打包脚本与 CI 的预置数据库步骤不同 | 统一发布组装规则，避免两套逻辑随版本漂移 |
| P1 | 已有 fake device、图像 fixture、计时器/身份能力和失败语义 | 扩展跨层场景回归，重点验证重复、过期、超时和恢复 |
| P1 | page.html 集中页面、样式及脚本；播放/业务协调文件较大，部分含大量测试 | 按职责渐进拆分，先区分生产代码与测试，不能仅按行数拆文件 |
| P1 | 运行涉及管理员权限、画面配置、DLL/OCR 资源、WebView2 和平台登录 | 首次运行向导、环境预检和可操作错误提示优先于新菜单 |
| P2 | 已有多种玩法、自定义工作流和 AI 能力 | 在主链路稳定后统一扩展规范，再按需求增加功能 |

### 具体代码切入点

以下均为有限静态审查结论，不能当成已复现故障：

| 顺序 | 代码事实 | 潜在风险与渐进动作 |
| --- | --- | --- |
| 1 | src/features/playback/controller.rs 的 PlaybackStatePort::confirm_playback_and_dequeue 默认仅调用 update，claim_terminal_outcome 默认返回 true；生产适配器已有原子实现 | 风险是未来适配器/替身静默弱化事务和去重保证，不是当前生产事务缺失。先补端口契约测试，再将关键保证改成显式必实现，简化实现仅留在明确的测试替身 |
| 2 | src/runtime/business.rs 的 request/request_value 使用 recv 等待，send_request 在锁外阻塞 send | 无超时本身不证明死锁；慢处理可能拖延共享调用。先测排队/处理耗时并注入失败，再确定截止时间与协作取消；超时不等于未执行，不能盲重试副作用 |
| 3 | src/composition/application.rs 的 FormalTaskExecutionContext::facade 重建 ApplicationRuntime，将多个 runtime owner 设为 None，并新建部分生命周期状态 | 两种运行时形态和重复字段映射提高后续遗漏同步的风险。逐步把 execute_pending_task/execute_web_tool_request 移入明确执行上下文，最后移除 facade；不整体重写 |

以上应分别形成小变更：端口保证优先，等待/取消以测量和故障测试为前提，组合层整理放在行为回归已覆盖之后。播放生产适配器已实现原子确认，现有保护应保留。

## 3. 分阶段推进

按里程碑推进，不承诺具体周数或版本号。P0 完成后再把 P1 大规模并行展开。每阶段验收未通过时，优先修复而不是继续堆功能。

### M0：收口当前变更，建立发布基线（P0）

**交付：**

- 将当前点歌榜工作整理成独立逻辑变更；保留既有用户改动，由维护者确认提交范围。
- 增加 Windows PR/push 质量工作流：格式检查、基础 crate 测试、具备原生依赖环境的主程序回归；clippy 先建立基线，再逐步提升为阻断门禁。
- 明确测试层次：纯逻辑、fake runtime/HTTP 协议、真实 OCR fixture、真实游戏冒烟；不把最后一层硬塞进普通 CI。
- 将本地与 CI 共用的发布清单/组装步骤提取到同一脚本，保留模型哈希、依赖检查和每份安装独立生成令牌的行为。
- 补开发环境说明：Windows/MSVC、Rust、LLVM/libclang、FFmpeg/MNN 路径、可选 OpenVINO，以及确实需要的模型。

**验收：**

- 普通代码 PR 自动触发检查；tests/、构建脚本与配置相关变更不会漏跑。
- 点歌榜回归覆盖：播放成功计数、失败/未播不计、重复确认不重复计数、重启保留、时间窗口、limit 边界、身份映射、接口鉴权；先盘点现有测试，仅补缺口。
- 点歌榜历史数据没有可靠事件依据时不伪造回填；时间字段、统计口径和默认窗口与文档一致。
- 本地和 CI 产物采用同一明确的数据库初始化策略；不携带开发机 Cookie、令牌或运行数据库。
- 干净 Windows 环境可按手册启动，缺依赖时有明确原因。

### M1：让识别—命令—播放链路可回归（P1）

**交付：**

- 复用现有时钟、operation ID、UI fake device 和 fixture，构建少量跨层场景测试；必要时新增窄测试接口，不先造通用回放平台。
- 扩充脱敏截图/消息序列：一级/二级切换、启动进入新大厅、滚动历史、短暂空白、窗口消失、昵称近似与 OCR 错字。
- 为播放、搜索、UI、消息投递整理统一的操作结果说明：已受理、执行中、成功、失败、取消、结果未知。
- 整理超时、重试和重复回执策略；检查晚到响应是否会覆盖新状态，不预设现有代码有此缺陷。
- 在已有日志与监控上关联一次请求的识别、排队、解析、播放确认和回复，不额外建立独立状态真相来源。

**验收：**

- 已记录的关键场景能在不启动游戏时重复运行，结果稳定。
- 旧画面不产生新输入、历史消息不重复执行、已取消操作不因晚到响应复活。
- 未知结果不会触发盲目重试；恢复或停止的理由可从日志/面板找到。
- 候选选曲、切歌、歌词、队列恢复、大厅到期暂停等已有规则不被新测试或重构改变。

### M2：降低维护与部署成本（P1）

**交付：**

- 对播放协调和 business runtime 按生命周期、命令转换、状态投影、事件处理等实际职责拆分；先移动测试/纯映射，再评估运行时边界。
- 将 Web 页面逐步分离为请求客户端、状态展示、播放/配置/登录模块；保留现有部署方式，不以引入大型框架为目标。
- 加入首次运行预检：游戏进程、画面尺寸、截图能力、OCR 模型/DLL、音频设备、WebView2、登录状态。
- 为配置保存标明即时生效/重启生效；为数据库升级建立隔离副本上的迁移/失败恢复测试及备份恢复流程。
- 提供脱敏诊断导出和简洁恢复提示；导出不包含凭据、访问令牌和未经确认的私聊截图。

**验收：**

- 拆分不改变 HTTP 契约和聊天命令；原测试与代表性端到端冒烟通过。
- 常见故障能给出下一步动作，而不只是“操作失败”。
- 模拟迁移失败能保留原数据；恢复在测试副本验证，不能仅声称有备份。
- 新用户可以不手工编辑业务坐标/深层配置就完成默认受支持环境的启动检查；超出支持范围明确提示。

### M3：围绕房间体验扩展（P2）

在前面里程碑通过、并收到明确需求后，从下列方向择一迭代，不同时铺开：

| 候选方向 | 用户价值 | 必须先满足的条件 |
| --- | --- | --- |
| 点歌与房间运营 | 榜单、偏好、收藏/常用队列、适当的公平性提示 | 统计口径、身份、隐私和保留策略明确；不改变既有权限和去重规则 |
| 娱乐玩法维护 | 一致的报名、计时、退出、恢复与消息投递体验 | 先提取真实共性，不强行统一不同玩法规则 |
| AI 辅助 | 候选选曲解释、配置说明、受约束的玩法辅助 | 输出校验、超时、预算、降级；不让模型直接拥有无约束按键权限 |
| 受支持环境扩展 | 更多分辨率、主题/语言或 OCR 后端组合 | 有代表性 fixture、硬件/环境矩阵和真实维护需求 |

## 5. 衡量方式

目前没有可靠生产基线，以下是建议收集的指标，不是现有表现或已承诺 SLA：

- 点歌漏斗：识别到有效请求 → 接受 → 搜索/解析成功 → 播放确认成功；区分权限拒绝、重复请求、取消和故障。
- 延迟：排队等待、曲目解析、播放确认和聊天回复的 P50/P95，保留运行环境标签。
- 稳定性：重复执行事件、窗口丢失后的恢复结果、运行时异常退出、连续运行期间的内存趋势。
- 易用性：首次启动完成情况、配置错误分布、是否需要维护者手动介入。
- 发布质量：升级/恢复冒烟结果、回归耗时、漏带依赖和升级失败记录。

先在本地或经过用户同意的诊断中建立基线，再定量化目标；不要默认上传聊天、歌曲偏好、截图和凭据。

## 6. 暂缓事项

- 不因文件大而全面重写、拆微服务或引入插件 ABI。
- 不把尚未验证的跨平台、云托管、自动更新作为下一版本主目标。
- 不把“接入更多模型/音乐源/玩法”当作稳定性提升的替代品。
- 不删除 vendor、模型、本地运行数据或未跟踪工具来追求目录整洁。
- 不为重构绕过现有任务互斥、身份权限、令牌保护和隐私边界。
