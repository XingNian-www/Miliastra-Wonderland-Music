# 游戏状态探测与转换地图（调研）

> 本文只做调研记录：**未改动应用任何既有逻辑**。所有探测都通过应用自身的 HTTP 调试 API，用原子命令组合完成。

## 1. 为什么要做这件事

当前状态机只有 **5 个探测点**：

| 探测点 | 依据 | 位置 |
|---|---|---|
| 进入游戏文案 | OCR 命中"点击进入" | `startup.game_entry.gate_region` |
| 大世界锚点 | `world_wish_template` 模板 | `screen.world_wish_rect` |
| 好友面板 | `friend_panel` 模板 | 固定区域 |
| 返回按钮 | back 模板 | 固定区域 |
| 聊天标记 | 蓝/黄/粉三色模板 | `screen.chat_rect` |

真机实测盲区：

| 实际界面 | 状态机读数 |
|---|---|
| 千星奇域功能菜单 | `secondary:chat`（**误判**） |
| 好友 / 我的好友 | `primary_marker` |
| 好友 / 添加好友（搜索页） | `transition:unknown` |
| 玩家卡片 | `unknown`（`friend=3ms back=10ms marker=69ms state=unknown`） |
| 更多设置菜单 | `unknown` |
| 寻找队友 / 地图 / 队伍配置 / 颂愿 / 当前大厅 | `unknown` |

**几十个截然不同的界面被压成 5 类，且大部分是 unknown。**

## 2. "可信探测点"的判定标准

1. **可表达**：能用沙盒原生断言表达（`ocr_contains` / `template`），不依赖人工看图。
2. **时间不变**：同一界面连续采样 3 帧，块内像素最大差 ≤ 2。
3. **运动不变**：**一级界面额外做运动验证**——移动角色 0.9 秒 + 拖动视角后仍满足第 2 条。
4. **判别力**：与其它所有界面在同位置的最小平均绝对差（MAD）明显大于 0。
5. **原生验证**：用 `template` 断言实跑，目标界面通过、其它界面不通过。

> 第 3 条是本次踩出来的重点：界面是**动态**的，落在 3D 场景或动画上的点看着"固定"，一动就废。

## 3. 原生探测点原语（无需改代码）

| 断言 | 用途 |
|---|---|
| `ocr_contains` | 区域内 OCR 文本包含目标串 |
| `template` | 区域内灰度模板匹配 |
| `pixel` | 单像素期望值 + 容差 |
| `frame_difference` | 前后帧变化像素数量区间 |
| `dimensions` | 截图尺寸 |
| `window_foreground` / `window_available` | 窗口状态 |

约束与技巧：

- **沙盒断言**路径：模板 ≤ 32×32、搜索区域 ≤ 128×128，每次运行最多 4 个模板断言。
  （注意：这条限制**只作用于断言**；探测时更该用下面的 `/tools/template`，它的区域只受屏幕尺寸限制。）
- 分数公式：`score = 1 - 平均绝对灰度差(MAD)/255`。
- 断言失败会**报出真实分数**（`模板未命中: best=<score>, min=<min_score>`）。把 `min_score` 设为 `1.0` 强制失败即可**读出实测分数**——这是官方校准手段。

调用形状（请求体 camelCase，断言 snake_case）：

```json
POST /debug/run
{"taskId":"<task>","mode":"live","assertions":[
  {"index":0,"assertion":{"template":{"x":0,"y":128,"width":32,"height":32,
    "template_width":32,"template_height":32,"grayscale":[/*1024 个灰度值*/],"min_score":0.9}}}
]}
```

## 4. 一级界面的不动点实测（运动验证）

采样 3 帧：第 1 帧静止；第 2 帧前**按住 W 移动角色 0.9 秒**；第 3 帧前**从屏幕中心拖到右侧转动视角**。全屏 60×33 个 32×32 块统计：

| 指标 | 结果 |
|---|---|
| 总块数 | 1980 |
| 三帧后仍不变 | **346** |
| 随场景变化 | 1634 |

**约 83% 的画面是动态的——一级界面的探测点只能落在 HUD 固定元素，绝不能落在 3D 场景。**

最优不动点：

| 不动点(32×32) | 时间差 | 与最相似界面 MAD | 最相似界面 |
|---|---|---|---|
| (0,128) | ≤2 | **116.3** | 寻找队友 |
| (32,128) | ≤2 | 116.2 | 寻找队友 |
| (0,192) | ≤2 | 90.3 | 千星奇域首页 |
| (32,192) | ≤2 | 86.4 | 当前大厅 |

> 寻找队友是右侧浮层，会压住一部分大世界 HUD，因此它是最容易与一级界面混淆的界面。

## 4.5 搜索区域与模板尺寸：实测取舍（重要）

直觉上"区域和模板都放大"会更稳，但实测**只有一半成立**。

### 4.5.1 放大搜索区域会让判别力变差

在 128×128 区域内搜索 32×32 模板时，匹配器取**区域内最佳位置**的分数，位置越多越容易撞上相似内容。逐档扫描（数值＝**其它界面在该区域能拿到的最高分**，越低越好；本界面真阳性 ≈ 0.99）：

| 不动点 | r32 | r48 | r64 | r96 |
|---|---|---|---|---|
| 一级界面 (0,128) | 0.544 | 0.545 | 0.641 | **0.862** |
| 一级界面 (32,128) | 0.544 | 0.618 | 0.777 | **0.862** |
| 千星奇域功能菜单 (960,96) | 0.678 | 0.832 | **0.966** | **0.968** |
| 寻找队友 (1888,416) | 0.521 | 0.552 | 0.596 | **0.877** |
| 队伍配置 (1344,640) | 0.635 | 0.685 | 0.829 | **0.911** |
| 好友列表 (800,0) | 0.694 | **0.850** | **0.863** | **0.866** |
| 搜索页 (992,0) | 0.702 | **0.857** | **0.857** | **0.857** |
| 更多设置 (672,352) | 0.715 | 0.783 | 0.835 | **0.945** |

**结论：区域从 32 放大到 96，误报分数普遍上升 0.05–0.35，多处直接冲到 0.86–0.97 —— 与真阳性几乎不可分。**
`r48` 基本免费，`r64` 开始明显退化，**`r96` 以上不可用**。

### 4.5.2 放大模板（多点组合）确实能提升判别力

单个断言模板上限 32×32，但**每次运行可用 4 个模板断言**。把同一界面的多个不变点组成**签名**（要求全部命中），等价于放大模板：

| 界面 | 点数 | 单点最坏 | **组合最坏** | 改善 |
|---|---|---|---|---|
| 一级界面 | 2 | 0.701 | **0.544** | −0.157 |
| 颂愿 | 4 | 0.839 | **0.635** | −0.204 |
| 好友列表 | 4 | 0.725 | **0.561** | −0.164 |
| 搜索页 | 4 | 0.790 | **0.665** | −0.125 |
| 当前大厅 | 3 | 0.666 | **0.547** | −0.119 |
| 千星奇域功能菜单 | 4 | 0.706 | **0.603** | −0.103 |
| 队伍配置 | 4 | 0.696 | **0.609** | −0.087 |
| 玩家卡片 | 4 | 0.811 | **0.729** | −0.082 |
| 更多设置 | 3 | 0.723 | **0.676** | −0.047 |
| 寻找队友 | 2 | 0.548 | **0.507** | −0.041 |
| 千星奇域首页 | 3 | 0.618 | **0.588** | −0.030 |
| 地图 | 1 | 0.690 | 0.690 | — |

多点组合把最坏误报压到 **≤0.729**（多数 ≤0.67），因此 `min_score = 0.80`（玩家卡片取 0.75）即可干净分离。

### 4.5.3 推荐设计（只用沙盒断言）

```text
每个界面 = 一个 4 点签名
  每点：模板 32×32（从冻结帧裁切）
        搜索区域 48×48（略微容忍位移，几乎不损失判别力）
  4 个断言同属一次运行、同一个 capture 索引
  要求全部命中 → 判定为该界面
```

**要点：模板靠"多点"放大，区域只做小幅容忍。** 若坚持要"单个大模板 / 超大区域"，需要放开代码里的校验上限（模板 32、区域 128）；但本实测说明**区域上限不是瓶颈**——真正制约判别力的是区域本身，越放大越容易误报。

## 8. 动态内容与注意事项

1. **粘贴会静默丢失**：点输入框后等待不足（< 约 700ms）时粘贴不生效，但所有命令都返回成功、输入框为空。属**无错误上报的失败**，流程内应加"粘贴后校验非空"。
2. **过渡态会被截到**：搜索页刚打开时截图可能得到半透明过渡帧（本次 `state-friend_search` 即如此），判据需等待 settle。
3. **玩家卡片页无分类标签**：分类器稳定输出 `state=unknown` 十余秒不收敛，纯日志判据的恢复流程会卡死，需要"有界探测"回退。
4. **一级界面必须运动验证**：静止 3 帧会让 83% 的动态画面"看起来是固定点"。

## 8.5 更正：发现接口其实存在（我先前判断有误）

应用早已提供**无需改代码**的探测接口，先前我用"解析日志 + 32×32 断言"是走了弯路。

### 8.5.1 UI 状态查询接口（存在）

```text
POST /tools/ui-state            # 排队一次 UI 状态检测
GET  /tools/task?id=<id>        # 取结果（异步）
```

实测（游戏未运行时）：

```json
{"id":1,"label":"UI 状态检测","status":"failed",
 "result":"错误: UI routine failed at capture_frame (BeforeInput): 未找到目标游戏窗口进程: yuanshen.exe,GenshinImpact.exe"}
```

它内部执行 `game_ui.capture()` 后取 `runtime.latest_ui_state().diagnostic()`，返回**带证据的状态诊断**。
→ 恢复流程**不应解析日志**，应直接用这个接口。

### 8.5.2 模板匹配接口（区域可整屏）

```text
POST /tools/template?template=<名称>&rect=<x,y,w,h>&threshold=<0..1>&click=<bool>
GET  /tools/task?id=<id>
```

- `rect` **只被 clamp 到屏幕尺寸**，实测 `rect=0,0,1920,1080` 被接受——**没有 128×128 限制**。
- 支持 19 个内置模板名（`friend-panel`、`friend-search-panel`、`friend-more-settings`、`friend-blacklist`、`friend-block-chat`、`friend-confirm`、`paimon-menu`、`world-wish`、`secondary-back`、`secondary-hall` …）以及 `Custom:<名称>`。
- 不带 `click` 返回**命中列表与分数**；带 `click=true` 会点最佳命中并返回 `已点击 <模板>: x=… y=… score=…`。
- 可用模板清单：`GET /tools/templates`。

**因此先前的探测点（区域=模板=32×32，零容差）偏紧**：正确做法是用大区域（乃至整屏）搜索小模板，天然容忍位移与轻微漂移。

### 8.5.3 其他可用工具

`/tools/ocr`（可指定 rect）、`/tools/scan-chat`、`/tools/hall-name`、`/tools/click`、`/tools/key`、`/tools/templates`。

## 9. 与现有状态机的差距（建议补充的探测点）

| 建议 | 理由 |
|---|---|
| 增加"一级界面前景遮挡"判据 | 寻找队友 / 地图等浮层会保留大部分 HUD，单点匹配不足以判定"回到一级界面"，需配合浮层探测点做**组合判定** |
| 为 11 个高频界面各加 1 个 32×32 模板点 | 消除 `unknown` 盲区，使流程能判断自己停留在哪个界面 |
| ESC 语义显式建模为"切换" | 避免恢复流程在一级界面误开菜单 |
| 探测点需通过运动/时间不变性验收 | 否则会在真实游玩中随机失效 |

- 本次所有观测都在**千星奇域大厅**环境；提瓦特主世界、战斗、剧情等状态未覆盖。
- 未覆盖同一界面的**滚动 / 分页 / 子标签**等内部状态。
- 状态清单来自按键与点击探测，不代表游戏全部界面。

## 11. 复现与运维要点

- 探测脚本：`dist/sandbox-run/capture-samples.ps1`（不变性采样）、`grid32.ps1`（32×32 扫描）、`verify-anchors.ps1`（原生验证）、`anchor-matrix.ps1`（锚点判别矩阵）、`restore-primary.ps1`（恢复一级界面）。
- 持久化提权重启：`dist/sandbox-run/app-control.ps1 -Action install|restart|status|stop`。
- **沙盒存储上限**：`max_tasks = 256`、`max_runs = 1024`，容量满会拒绝新增且**没有删除接口**。
  - **任务与运行都会持久化到 SQLite journal 并在启动时恢复**（`with_journal` → `journal.tasks()` / `journal.runs()`），所以**重启不会清空**（先前"重启即清零"的判断是错的）。
  - **更新已存在任务只校验版本递增、不检查容量** → 探测时应"复用同一个任务 + 递增 version"，循环中只新建运行，否则很快耗尽。
  - `/clear-history` **只清 HTTP 命令历史**（`state.history`），与沙盒存储无关。
  - 不自动淘汰是**刻意的证据优先策略**（存储注释： "容量满时拒绝新增，保留已有证据"）；journal 侧只对运行证据保留 64 条（`MAX_RECORDS = 64`）。
