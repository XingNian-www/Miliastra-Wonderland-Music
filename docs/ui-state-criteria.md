## 2. 奇域主菜单　`main_menu`

| | |
|---|---|
| **示例图** | ![](ui-state-evidence/transition-to-overworld/02-hub-menu.jpg) |
| **判据** | 左上返回按钮命中**之后**，再看 `(1740,1005) 100x40` 区域内「返回提瓦特」按钮模板；命中即判主菜单 |
| **实测** | 8 张主菜单帧里 6 张**稳定帧**模板 score **1.0000**（另 2 张是淡出过渡帧，见下）；同帧 `secondary-back` 也命中 **0.9782** |
| **理由** | 主菜单是**叠在大厅上的浮层**，它复用了大厅和二级界面共有的那个**圆形返回按钮**，所以只靠返回按钮分不开；但它右下角多一个「返回提瓦特」按钮，二级界面没有 |

**为什么必须先判它**：不先判，主菜单会被 `secondary-back` 判成二级聊天（历史缺陷，8/66 帧）。

**判断依据的可复现性**：
```powershell
# 6 正样本必须命中、11 负样本必须不命中、3 真二级必须仍是 secondary
cargo test --lib main_menu_is_classified_before_secondary_back
# 主菜单连刷 5 帧绝不能被回退误报成 overworld
cargo test --lib hub_menu_never_falls_through_to_overworld_after_unknown_grace
```

**已知反例（如实列出）**：
- `step-5.png` / `step-last.png` 是**菜单淡出过程中的过渡帧**，按钮只剩约两成不透明度，
  模板抓不到，会落到 `secondary_back`。**这是有意的**：给淡出帧加特判就是拿观测凑结果。
  实机风险有限——过渡帧不稳定，应用只在稳定类型变化时才推 `ui.state` 事件。
  已用特征化断言钉住，行为一变测试就失败。

## 5. 提瓦特大世界　`overworld`

| | |
|---|---|
| **示例图** | ![](ui-state-evidence/transition-to-overworld/05-overworld-teyvat.jpg) |
| **判据** | 祈愿图标模板，**仅在连续两帧 Unknown 之后**的回退路径里使用 |
| **实测** | 实机从千星出来时事件 41 判出 `overworld stable=true`，规则 `world_wish_template` |
| **理由** | 大世界右上角有固定的图标栏；但**这个模板本身没有判别力**（语料里命中 40/66 = 60%） |

**⚠️ 用它的唯一前提是"闸门"**：它只在别的判据都判不出来时才被问到。
反过来说，**任何长期停在 `unknown` 的界面都可能被它误报成 overworld**——
奇域主菜单就出过这个事故（见 §2 的第二个测试）。

**已经实证过两次**：

1. **奇域主菜单**——落 `unknown` 后被误报（见 §2 的第二个测试，已修）；
2. **登录界面**——冷启动 +20s，画面是云上天城登录界面（没有任何 HUD）却被报成 `overworld stable=true`，证据 `ui-state-evidence/login-screen.jpg`。**这一条尚未修**，已登记为缺陷。

⇒ **不要靠调 `world_wish` 的阈值去修**，那是拿观测凑结果。正解是给这些界面补真正的判据。

### 5.2 提瓦特的世界聊天会触发「千星大厅」判据

提瓦特大世界的**世界聊天**同样带蓝/黄/粉气泡，于是 `primary_chat_markers` 命中，
把**提瓦特判成千星大厅**。

- 证据：见 `ui-state-evidence/cold-start/enter-2.jpg`（提瓦特 HUD + 左下「[咸鱼小呆瓜]:摘计算机」）

⇒ **聊天标记不是千星奇域独有**。**第 48 节已修**：
标记路径现在还要求底栏近白像素占比 ≥ 8.219%（大厅底栏有多个白色按键，提瓦特只有一个 `Enter`）。
实测提瓦特 3.0–3.8%、大厅 ≥ 11.181%，两者之间无帧；阈值取区间中点。
副作用：`wonderland-collection.png` 那条"平坦蓝底被当成蓝标记"的旧缺陷也一并修掉了。
**注意**：另一条缺陷（**加载界面被误报成 overworld**）仍未修。

**尚未采用但更强的候选**：大厅底部条是 `💬 Enter | 👥 O | 🔊🏛️ Alt+N | 🎤 N`，
提瓦特是 `Enter | Space E Q`。**两者完全不同**，是一条不依赖 OCR 的强判据候选；
但需要更多提瓦特帧才能立判据，**本轮不立**。

> **第 56 节补充：这条候选已实测证伪。** 大厅底栏会随「是否有人发言」**上下移位并缩放**。
> 用「无人发言」布局切出 Enter 按钮当模板，跑应用同款**灰度 1:1 SAD**，得到：
> 大厅无人发言 **0.9097** ✓、大厅有发言 **0.9022** ✓ / **0.8833** ✗、登录界面（负）**0.8731**。
> **正负只差 0.029**，模板匹配**无法稳定分离** ⇒ 不能做判据。
> 底栏真正可用的是**整区像素占比**（§1 的近白否决）：大厅最低 10.965%、非大厅最高 5.257%。

## 9. `loading`（加载界面）

**为什么它必须是一个状态**：以前加载界面只能落在 `unknown`，但它是**确定的、可观测的界面**，
而且实测**有两种外观**，长期占着 unknown 会让"unknown"这个诚实信号失去意义。

### 9.1 判据（整屏像素占比，与位置/缩放无关）

| 外观 | 判据 | 实测区间 | 最接近的真实画面 | 切点 |
|---|---|---|---|---|
| **黑底徽记型**（传送等短加载） | 暗像素(<40) 占比 ≥ **62.23 %** | **98.46 ~ 98.53 %** | **26.00 %**（活动面板） | (26.00+98.46)/2 |
| **白底元素型**（冷启动进世界） | 近白(min(R,G,B)≥200) 占比 ≥ **71.54 %** | **99.77 ~ 100 %** | **43.31 %**（登录界面） | (43.31+99.77)/2 |

- 取样：每 **20 像素**取一点，`v = 0.299R + 0.587G + 0.114B`
- **适用域**：整屏截图（≥1280×720）。小裁剪图（按钮、色条）不参与这条判据
- 两条规则的余量都 **> 56 个百分点**，**不需要凑阈值**

| `loading-screens/loading-dark-A.jpg` | 黑底加载（用户点传送那次） | `loading/loading_dark_screen` ✅ |
| `loading-screens/blank-frame.jpg` | 全白 | `loading/loading_white_screen` ✅ |

## 10. 世界判别：提瓦特 vs 千星（第 57~58 节）

**为什么它必须是一个独立维度**：`primary`（千星大厅）和 `overworld`（提瓦特大世界）
是两个不同的状态，但它们的**底栏、小地图、队伍列表全都存在且样式相近**，
历史上一直靠底栏图标模板与一条很可疑的 OCR 判。本节给出一条**不依赖底栏、不依赖 OCR、
不依赖场景内容**的确定性判据。

### 10.1 判据

```
1. 取整帧左上角 220×230 的 HUD 角
2. 判据只用其中 (40,37)-(71,76) 这 32×40 = 1280 像素（派蒙头像 + 千星装饰盘边缘）
3. 在该区域上做 ±2 像素搜索
4. 对每个候选偏移做逐通道归一化：v' = (v - 区域均值) / 区域平均绝对偏差
5. 与两组冻结参考（4 张标注提瓦特 + 6 张标注千星的组均值，同样归一化）算每通道平均绝对差
   各自取搜索范围内的最小值 dT / dQ
6. 判定：
      min(dT,dQ) > 0.5   ⇒ unknown（理由 hud_absent：全屏菜单/加载界面）
      max/min >= 2.0     ⇒ 返回较近的一侧（提瓦特 / 千星）
      否则                ⇒ unknown（理由 ambiguous）
```

**参考帧是冻结的**：4 张提瓦特（`anchor-teyvat-56/w-00..03`）+ 6 张千星（`anchor-user-56/u-01..06`），
自第 56 节标注后**从未改动**。

### 10.9 更鲁棒的形态：青色条纹带标量（推荐）

app 第 48 节已经确立过先例：**用区域上的标量统计，而不是 1:1 模板匹配**，
因为标量对位移和缩放都不敏感。世界判据应当照这个形态做。

**区域**：`(76,60)-(93,84)`（把 220×230 裁剪内的坐标，18×25 = 450 像素）
**规则**：统计满足 **`(G-R)>30 且 (B-R)>30`** 的像素数（**相对色差**，不是绝对亮度阈值）
**判定**：`count >= 100` ⇒ 千星；`count <= 50` ⇒ 提瓦特；中间 ⇒ Unknown

实测（留出帧，缩放 1.0）：

所以**真实空档是 28 → 194**（约 7 倍），不是 0 → 194。阈值 100 落在空档内。

**鲁棒性对比**：

| 扰动 | 绝对规则 R1（`G>150 且 B>150 且 R<130`） | **相对规则 R2（本文推荐）** | 归一化模式匹配 |

### 10.10 落地时踩到的门：只能是 HUD 在场检测，不能是界面 kind

**第 58 节把青色标量接进证据链后，线上实测立刻发现一个自信判错**：

| 帧 | kind | count | guess（第一版，无门） |
|---|---|---|---|
| 千星大厅（喷泉） | `primary` | 200 | `qianxing` ✅ |
| 千星大厅（沙滩） | `primary` | 346 | `qianxing` ✅ |
| **派蒙菜单** | `secondary` | **0** | **`teyvat`** ❌ |

**根因**：青色标量**没有 HUD 在场检测**。全屏菜单（派蒙菜单、奇域枢纽菜单、提瓦特地图…）
的左上角是**菜单内容**，青色计数恒为 0，与提瓦特的 0 无法区分。
归一化模式匹配有 `hud_absent` 门（`min(dT,dQ) > 0.5`），标量没有 —— 这正是 `10.9 推荐的
"两者结合"里被我省掉的那一半。

**第一版修法（已上线）**：给 `world_probe_evidence` 加 `hud_state` 参数，
**只有 kind 属于 `primary` / `overworld` 时才跑世界判定**，其余状态结论固定为
`not_applicable`（计数照样报出来便于复核）。回归测试
`world_probe_never_guesses_a_world_outside_hud_states` 覆盖 8 帧菜单/地图/背包/祈愿。

**但这道门还不够**：app 里 `overworld` 这个状态**只能靠"连续 2 帧 unknown"的回退得到**，
单帧离线路径永远返回 `unknown` —— 所以按 kind 做的门**同时把提瓦特侧也挡住了**：

| 帧 | kind | count | guess（第二版，按 kind 门） |
|---|---|---|---|
| 提瓦特雪山 | `unknown` | 18 | `not_applicable` ❌ 本该是 teyvat |
| 提瓦特沙漠 | `unknown` | 0 | `not_applicable` ❌ |
| 派蒙菜单 | `secondary` | 0 | `not_applicable` ✅ |

**不能简单把 `unknown` 放进门里** —— `unknown` 里同时包含全屏菜单，
放进去就把上面那个 bug 放回来了。

**正确的门**：用**归一化模式匹配的 HUD 在场检测**（`min(dT,dQ) <= 0.5`，
实测 HUD 在场最大 0.0844 / 不在场最小 1.1172，13 倍空档），**而不是界面 kind**。
代价是把两组参考在 `(40,37)-(71,76)` 上的均值块作为资源带上，共 1280×3×2 = **7680 字节**。

**当前状态**：只在千星大厅（`primary`）上给世界结论，提瓦特侧拒判。
这是**诚实但半边的能力**，不得声称已完整支持。

### 10.11 盖革式弱点实测（第 58 节：用 app 自己的分类器喂扰动帧）

做法：把原始帧按下表扰动后**喂给 `/debug/ui-state`**（即 app 分类器本体），
看它给什么结论。**不预设答案**：只要不是自信判错就算合格。

| 扰动 | hall3（千星） | snow（提瓦特） | paimon（菜单） |
|---|---|---|---|
| 原帧 | qianxing（200） | teyvat（18） | not_applicable |
| 右移 1px | qianxing（200） | teyvat（22） | not_applicable |
| 左移 1px | qianxing（201） | teyvat（16） | not_applicable |
| 右移 2px | qianxing（190） | teyvat（25） | not_applicable |
| 左移 2px | qianxing（199） | teyvat（15） | not_applicable |
| 右移 3px | **not_applicable**（180） | **not_applicable**（29） | not_applicable |
| UI 缩放 0.85 | **not_applicable**（13） | **not_applicable**（0） | not_applicable |
| UI 缩放 1.15 | **not_applicable**（30） | **not_applicable**（24） | not_applicable |
| 分辨率 1280×720 | **not_applicable**（0） | **not_applicable**（0） | not_applicable |

**结论（重要）**：所有弱点**都表现为拒判，没有一次自信判错**。

- **位移 ±1 / ±2 全对** —— 这就是第 57 节给 ±2 像素搜索换来的；不允许搜索时 ±1 就翻判断。
- **位移 ±3 拒判** —— 超出搜索窗口 1 像素。是拒判不是判错，符合纪律。
- **UI 缩放拒判** —— 与第 57 节离线结论一致（缩放是**覆盖**限制不是正确性缺陷）。
- **分辨率 1280×720 拒判** —— 这一条值得单独说。

**分辨率那条为什么拒判**：`classify_at` 会把非 1920×1080 的输入
`resize_exact(1920,1080, Triangle)` 归一到标定分辨率，所以**尺寸本身不是问题**；
问题是**上采样把细条纹抹掉了**，青色条纹带被糊没。实测原始帧本应算 200 个青色像素，
上采样后只剩 **0 个**。

**⇒ 这说明门是必需的，不是保险丝**：1280×720 的千星大厅帧，青色计数 0 会落进
"提瓦特"那一侧（≤68），**如果没有 HUD 在场门就会自信判成提瓦特**。
门把它拦成了 `not_applicable`。

**⇒ 已知覆盖边界（不隐瞒）**：这条判据在**原生 1920×1080** 上成立；
UI 缩放或换分辨率后它拒判而不是给答案。app 实机截图就是 1920×1080，
所以实机可用；但这不是一条分辨率无关的判据。

**下一步的改进方向（已离线量过，未实现）**：把参考与样本都做**分块平均**再比。
第 57 节量过 8×8 分块的平均绝对差分离度是 **2.28**，比逐像素的更稳；
分块平均天然吸收缩放与上采样模糊。

### 10.12 尺度搜索：从"整片拒判"到"1.15 能判、0.85 仍拒判"

第 58 节试过给 HUD 在场检测加**尺度搜索**（每个采样格点取对应大小窗口的平均，
scale != 1 即降采样），范围 ±15%，并以"达到最佳距离的尺度"作为世界判据量青色时用的尺度。

**踩到的坑（值得记）**：第一版只缩放了采样**步长**，没有缩放区域**原点**：

    let left = rect.x as f32 + i as f32 * scale;    // 错

UI 整体被缩放时，区域的**原点会同步移动**，正确写法是

    let left = (rect.x as f32 + i as f32) * scale; // 对

只缩放步长的话，0.85 / 1.15 的帧**无论怎么搜都找不到参考**，现象是加了尺度搜索
完全没有效果。这个坑是靠**离线实验与线上实测对不上**发现的：离线脚本写的是
`X0*s + bi*bs*s`（原点跟着缩，对的），线上 Rust 写的是错的，两边结论矛盾，
回头查才发现。

**修好后的线上实测**（24 帧扰动，喂 /debug/ui-state）：

| 扰动 | hall3（千星） | snow（提瓦特） | paimon（菜单） |
|---|---|---|---|
| 位移 1px | qianxing（200） | teyvat（22） | not_applicable |
| 位移 3px | **not_applicable**（180） | **not_applicable**（29） | not_applicable |
| **UI 缩放 1.15** | **qianxing（227）** | **teyvat（11）** | not_applicable |
| UI 缩放 0.85 | **not_applicable**（13） | **not_applicable**（0） | not_applicable |
| 分辨率 1280×720 | **not_applicable**（0） | **not_applicable**（0） | not_applicable |

**结论**：尺度搜索**部分**解决了 UI 缩放 —— 1.15 从"拒判"变成"判对"，
0.85 仍然拒判。**没有出现任何一次自信判错**：所有没判对的格子都是 `not_applicable`。
菜单侧在 1.15 / 0.85 / 1280×720 下**依然全部拒判**，说明放宽搜索范围没有把菜单放进来
（这一点由 `hud_presence_is_separated_by_reference_distance` 那条区间不重叠断言守着）。

**为什么 0.85 不行、1.15 行**：放大是把同一份结构铺开，粗结构还在；
缩小是把细节压没，比放大更容易丢掉参考里依赖的细结构。**这是已知覆盖边界**，
不是判错的理由 —— 缩小后它拒判。

**仍然做不到的**：分辨率 1280×720 经 `resize_exact` 归一后细节被抹，0.85 缩小同理。

```
OFFLINE: kind=unknown   | rule=no_reliable_anchor                   <- 对（同一块画面）
```

**同一个画面、两条路径给出矛盾结论**，而且**与顺序无关**（先截图再查、先查再截图都一样）。

### 15.3 根因：回退探针只看一个模板

`src/interfaces/http/routes/debug.rs` 的注释早就写明了差别：

> 实时路径只有在**连续 2 帧**都判 unknown 后才会走 `probe_game_state`，单帧离线分类永远到不了那里。

而 `probe_game_state` **只看右上角祈愿顶栏一个模板**：命中就报 `overworld`。
千星大厅的多人面板连续给出 `unknown` ⇒ 触发回退 ⇒ 祈愿顶栏**命中了** ⇒ 自信判成大世界。

**这不是新风险**：仓库里 `hub_menu_never_falls_through_to_overworld_after_unknown_grace`
的注释写着「world-wish 在语料里命中过 **60%** 的帧」，
第 46 节甚至因此把提瓦特判成了千星大厅。之前那条防护只覆盖了主菜单，
**没覆盖 F2 多人面板**。

### 15.4 修法：给回退探针叠一道正交的世界判据

`src/ui/state.rs` 新增 `world_is_teyvat(image)`：**既要 HUD 在场，又要判为提瓦特**。
`probe_game_state` 里祈愿顶栏命中后**必须再过这道门**才算大世界，并给出新判据名
`world_wish_without_teyvat_hud`——让误判在日志里**一眼可见**，不再伪装成正常的大世界判定。

**踩到的坑（值得记）**：第一版写成了 `world_hud_distances`，而正确的是 `world_hud_scale`。
前者**没有 HUD 在场门**，全屏面板会被放行，而面板左上角的青色计数接近 0，
于是又被自信判成提瓦特——**新写的回归用例当场把它抓住**，改成带门的版本才对。

**回归用例**：`probe_game_state_rejects_world_wish_hits_outside_teyvat`
用**真实的三帧千星面板**做负样本、`snow-01`/`desert-01` 两帧真实提瓦特大世界做正样本，
既证明门拦得住，也证明没把门关死。

### 15.5 顺带修正的既有用例

`classifier_keeps_chat_priority_and_probes_game_states_only_after_unknown_grace`
用的合成帧**只有一块祈愿顶栏、没有真实提瓦特 HUD**，加门之后它不再是 `Overworld`——这是**正确**的。
用例真正要测的是**回退时机**，所以改成把两个时刻都钉住：

- 第 31 秒：探针跑了 ⇒ `label()` 是 `unknown`，而 **`evidence().final_rule()` 是门的那条规则**；
- 第 32 秒：还在 5 秒冷却里 ⇒ `final_rule()` 回到 `no_reliable_anchor`，OCR 次数也少一次（3 不是 4）。

这样既证明「探针确实跑了」，又证明「门确实生效」，比原来只看 kind 更强。

## 16. 千星大厅多人面板（F2）：不动点模板判据（第 60 节）

### 16.1 方法：不做整帧模板匹配，做"区域归一化描述子 + 冻结参考比距离"

先把三帧 F2 面板（**玩家列表各不相同**）逐格比一遍，找**逐像素恒定**的区域——
结论是**一个都没有**（JPEG 噪声 + 背景粒子动画，任何 160x160 大块的最大通道差都 ≥ 13）。
所以走项目里已经验证过的路子：与世界判据同一套——**减通道均值、除平均绝对偏差后再比距离**。

### 16.2 区域候选实验（不是拍脑袋选的）

三帧正样本 + 30 帧其他界面，5 个候选区域全部量了一遍：

| 候选区域 | 正样本最大距离 | 负样本最小距离 | 倍数 |
|---|---|---|---|
| 左侧大厅卡片 `x2..35 y10..45` | 0.0340 | 1.0809 | **31.8x** |
| 整个底栏 `y60..68` | 0.0447 | 1.1254 | 25.2x |
| **底栏左半 `x0..60 y60..68`** | **0.0460** | **1.0982** | **23.9x** |
| 底栏中右 `x40..90 y60..68` | 0.1080 | 0.9530 | 8.8x |
| 左侧「当前大厅」标题 `x2..20 y1..8` | 0.0702 | 1.0194 | 14.5x |

**选「底栏左半」**：它是**纯界面骨架**（「大厅列表」「新建大厅」两个按钮所在的那条底栏），
既不依赖玩家内容、也不依赖大厅名字与人数。虽然左侧大厅卡片倍数更高，
但那一块**含大厅名与人数**，拿它当不动点容易把"换了个人在大厅"当成判据。

阈值取**对数中点**：`sqrt(0.0460 x 1.0982) ≈ 0.2248` ⇒ **0.22**（与世界判据同一套取法）。

### 16.3 落地

- 冻结参考 `assets/qianxing-f2-ref.bin`（2904 字节 = 24 头 + 480 格 x3x2），
  生成脚本 `dist/qianxingdata/mkf2ref.py`，格式 `MWF2` + 版本 + w/h/x/y + 归一化 i16（x1000）。
- 区域用**格索引**表达（120x68 网格，第 (cx,cy) 格的采样点是 `(cx*16+8, cy*16+8)`），
  与做实验时的口径逐字一致。
- 判据 `is_qianxing_player_panel` / `qianxing_player_panel_distance`，
  接在分类器里**`Unknown` 之后、回退探针之前**：既不会抢走已有状态，也不会再被回退探针误认成大世界。
- 用例 `qianxing_player_panel_is_separated_by_reference_distance`：断言**两侧区间不重叠**、
  阈值严格落在空档内、小裁剪图拒判。**负样本里特意放了千星大厅本身**（`start-hall`、`hall-again`），
  因为"大厅"和"大厅里的 F2 面板"必须分开。

### 16.4 踩到的坑：测量脚本钳位了，Rust 没钳位

最后一行格心是 `67*16+8 = 1080`，而 1080 行画面的有效行是 0..1079。
dump 脚本当初写了 `if y >= height { y = height-1 }`，Rust 里漏了，
于是**正样本直接"量不出来"**（返回 `None`），被分离度用例当场抓住。已补上同样的钳位。

这类"测量口径与实现口径不一致"是这套方法最容易翻车的地方，
所以每个常量注释里都写死了采样口径，改口径必须重新量阈值。

### 16.5 诚实记录：判据偏脆，但它**从不说错话**

拿 4 帧真实 F2 面板量距离（阈值 0.22）：

| 帧 | 距离 | 结果 |
|---|---|---|
| `qianxing-ui-59/qxf2-from-hall.jpg` | 0.0000 | 命中 |
| `qianxing-ui-59/after-fix-f2.jpg` | 0.0460 | 命中 |
| `qianxing-ui-59/r10-now.jpg` | 0.0467 | 命中 |
| `qianxing-ui-59/r10-set.jpg`（面板稳定后的实时帧） | **0.7483** | **未命中** |
| 负样本（30 帧） | ≥ 1.0982 | 全部未命中 |

**0.7483 落在正样本（0.047）与负样本（≥1.098）之间**，是一个**明确落在空档里的中间值**。
也就是说这一帧判据**看不出**它是不是 F2 面板——按目标的纪律，
**此时必须显式返回 Unknown，而不是猜一个**。分类器确实返回了 `Unknown`。

**⇒ 判据是"安全但不完整"的**：命中时答案对，拿不准时拒判，**不存在自信说错话的情况**。

**还没查清**：`r10-set.jpg` 与 `r10-now.jpg` 肉眼看着是同一个面板，
但底栏描述子差了 16 倍。可能是动画未完全结束、或底栏某个元素（如状态文字、悬停高亮）
在两次抓帧间不同。**在没有查清之前不调阈值**——那正是"调阈值凑已观测结果"。
**下一步**应该是扩大正样本、定位底栏到底是哪个元素在变，而不是放宽阈值。

### 16.6 顺带确认：第 59 节的世界判据门在实机生效

本轮实时轮询里出现了 `rule=world_wish_without_teyvat_hud`（2 次）——
说明**祈愿顶栏确实在千星面板上命中了**，而**门把它拦下了**。
这正是第 59 节要证明的那件事，现在在真实运行中看到了。

全部喂一遍扰动帧，**端到端走 app 真实分类器**（`/debug/ui-state?image=`），不是离线近似。

### 17.3 原始数值（为什么是拒判而不是判错）

**千星地图判据**（阈值 `dark%>=0.32` 且 `darkTeal%>=0.64`）：

| 扰动 | dark% | darkTeal% | 结果 |
|---|---|---|---|
| 基准 | 0.3750 | 0.7441 | 命中 |
| 位移 ±1 | 0.3743 ~ 0.3754 | 0.7424 ~ 0.7451 | 命中 |
| 位移 ±2 | 0.3746 ~ 0.3754 | 0.7433 ~ 0.7449 | 命中 |
| 位移 ±3 | 0.3746 ~ 0.3750 | 0.7444 ~ 0.7464 | 命中 |
| 1280x720 | 0.3751 | 0.7488 | 命中 |
| UI 0.85 | 0.5478 | 0.5293 | 拒判（暗占比过高、暗青不足）|
| UI 1.15 | 0.2447 | 0.7013 | 拒判（暗占比不足）|

不是模板匹配——这正是第 55 节选它的原因。分辨率同理（`0.3751`，与基准差 0.0001）。

**F2 面板判据**（阈值 距离 `<=0.22`）：

| 扰动 | 距离 | 结果 |
|---|---|---|
| 基准 | 0.0000 | 命中 |

阈值 **0.22**——只有 10% 余量，等于站在悬崖边上。项目里世界判据早就踩过同一个坑
（第 57 节："不允许平移时 ±1 像素就翻判断"），修法是加 ±2 搜索。本轮照做，

连"千星大厅本身平移后也不许命中"一并断言。

### 17.4 已知的真实局限（写清楚，不粉饰）

1. **世界判据在 1280x720 与 UI 0.85 下拒判。**
   这不是判错，是**量不到 HUD**——`classify_at` 先把画面归一化到 1920x1080，
   而 UI 本身缩小后，HUD 参考在搜索的 7 个尺度里都对不上。**待解决**。
2. **世界判据在位移 ±3 下拒判**（±2 在搜索窗口内所以全对）。
   这是第 57 节就记录在案的行为：超窗口 1 像素 ⇒ 拒判，符合纪律。
3. **千星地图与 F2 面板在 UI 缩放 0.85/1.15 下拒判。**
   两者的采样口径都是固定 16 像素一格，UI 缩放后格子对不上。
   **没有为了通过而放宽阈值**——放宽只会把"看不清"变成"猜一个"。
4. **UI 1.15 对世界判据是对的**（`hall3` 227、`snow` 11），
   这是第 58 节修掉"原点没跟着缩放"那个 bug 之后的结果，至今有效。

### 17.5 纪律声明

本节**没有为了让任何一项通过而调整阈值**。
唯一改动的 F2 判据加的是**平移搜索**（扩大可比范围），阈值仍是
第 60 节实验量出的空档中点 `0.22`；加搜索后正样本距离只会**变小**，
分离度只会**变好**，不存在"往已观测结果上凑"的空间。

### 19.7 踩到的坑：PowerShell 变量名大小写不敏感

清点脚本连续几次**全部请求失败**，而单帧手测正常。根因是：

```powershell
$H=@{ "X-Miliastra-Token"="123456" }   # 请求头
try { ...; $imgW=$im.Width; $h=$im.Height }   # $h 与 $H 是同一个变量！
```

**PowerShell 变量名不区分大小写**，`$h` 把请求头覆盖成了整数，
之后每个请求都不带 token，于是全失败。
（文档早就在「PowerShell 陷阱」里写过这一条，这次还是踩了。）
改成 `$imgW/$imgH` 后：**150 帧全部成功、0 失败**。

### 22.5 代码路径（已经读清楚）

```rust
pub fn screen_point(&self, point: PointConfig) -> ScreenPoint {
    let x = self.client_left + scale_i32(point.x, self.content_width, self.client_width);
    let y = self.client_top  + scale_i32(point.y, self.content_height, self.client_height);
}

fn click_screen(&self, enigo: &mut Enigo, screen: ScreenPoint) -> Result<()> {
    self.ensure_point_targets_window(screen)?;
    enigo.move_mouse(screen.x, screen.y, Coordinate::Abs)?;   // 先移
    enigo.button(Button::Left, Direction::Click)?;             // 再点
}
```

**⇒ 输入坐标空间是 `content_*`，屏幕空间是 `client_*`，中间做线性缩放；点击前一定先移动鼠标。**
所以"没悬停"和"坐标没换算"这两条都不是原因。

### 22.6 结论与下一步

**这不是 app 输入层的问题**（同一套 `click` 在 7 个别的坐标上全部生效），
**而是游戏对"面板内部点击"的接受方式还有别的条件**。

**下一步值得试的方向**：
1. **先移开再移回**：`click` 在一个 `move_mouse` 之后立刻 `button`，中间没有等待。
   游戏的 UI 可能是**每帧轮询光标位置**，同一毫秒内完成移动与点击会用到**上一帧的光标位置**。
   要给 `click` 加一个小停顿（或把 `move` 与 `button` 拆成两条命令），**这是目前最像原因的一条**。
2. 在宫格按钮上按下后**多等一会儿再抬起**。
3. 用键盘导航（方向键 + Enter）绕过鼠标。

**⇒ 本轮没有为了让点进去而横扫坐标范围试探**——那是碰运气，不是验证。
上面每条都对应一个明确假设与可判定的实验。

## 23. 宫格按钮问题已解决：给点击加 80ms 静默（第 67 节）

### 23.1 结论先行

**第 66 节的假设成立。** `click_screen` 在 `move_mouse` 与 `button(Click)` 之间没有任何等待，

### 23.2 改动

```rust
// src/adapters/windows/window.rs
const CLICK_SETTLE_MS: u64 = 80;      // 新增，与下面那组 DRAG_* 同一个道理

fn click_screen(&self, enigo: &mut Enigo, screen: ScreenPoint) -> Result<()> {
    self.ensure_point_targets_window(screen)?;
    enigo.move_mouse(screen.x, screen.y, Coordinate::Abs)?;
    sleep(Duration::from_millis(CLICK_SETTLE_MS));   // <-- 新增
    enigo.button(Button::Left, Direction::Click)?;
    Ok(())
}
```

```
2 现在      primary|primary_friend_template     <-- Escape 没打开菜单
3 点(180,695)
4 之后      secondary|secondary_back_template   <-- 点击生效了
5 点(295,695)
6 之后      primary                              <-- 回到大厅
```

看帧：

| 帧 | 内容 |
|---|---|
| `r20-menu.jpg` | **千星大厅**（不是菜单）|
| `r20-after-click.jpg` | **大厅的聊天/好友侧栏**（「当前大厅」+「公开频道」+ 玩家列表 + 发送），app 判 `secondary` **正确** |

**⇒ 三条结论**：

1. **第 67 节的 80ms 点击修复完好无损**——这一次点击确实换屏了，而且 app 判对了（`secondary`）。
2. **重采之所以全是大厅，是因为 Escape 没有打开菜单**——脚本却以为"已经在菜单里"就直接点击，
   于是每一下都打在大厅上。
3. **`Escape`（键盘）这次不生效，而 `click`（鼠标）生效**——所以现在脆弱的那个是键盘输入。
   （第 56 节曾经把"权限不对称"当假设并否掉过；这次观察到的现象是"键鼠不同命"，
   与当时的结论不矛盾——当时否掉的是"点击完全不能用"。）

### 26.3 真正的教训：脚本没有验证自己的前置条件

采集脚本的结构是：

```powershell
for($i=0;$i -lt 6;$i++){ if((Live) -match "main_menu"){break}; Escape }
Cmd click ...
Grab screenshot
```

**它假设"按够 Escape 就会在菜单里"，但从来没有验证过这个假设。**
当 `Escape` 失效时，`Live` 一直不是 `main_menu`，循环空转 6 次，然后**照样点击、照样截图**，
把大厅的帧当成子界面帧存了下来。

**⇒ 这是"采集脚本缺少前置条件断言"的典型错误**，和第 25 节那个"固定 3 秒"是同一类毛病：
**把没验证过的假设当成事实，然后拿它的产物当数据。**

### 26.4 修正方案（下一轮按这个改）

采集每一格之前必须**断言前置条件成立**，不成立就跳过并记一行原因，而不是硬着头皮采：

```
前置: Live 必须是 main_menu（= 奇域主菜单已打开）
      若 6 次 Escape 后仍不是 main_menu ⇒ 记录 "PRECONDITION_FAILED" 并跳过这一格
点击后: 必须等到 Live 不再是 main_menu（或画面稳定且与点击前不同）
       两者都不满足 ⇒ 记录 "NO_TRANSITION" 并跳过
```

**⇒ 这样采出来的每一张帧都自带"我确实是从菜单进去的"这个证据**，而不是靠事后看图猜。

### 26.5 本轮的净收获

- **确认 80ms 点击修复有效**（在全新一轮里又验证了一次，且 app 判据正确）；
- **拿到一张新的已验收帧**：`secondary` 聊天/好友侧栏（第 3 章那一类），
  证据 `qianxing-ui-59/r20-after-click.jpg`；
- **定位了重采失败的真因，并写清修正方案**；
- **没有把 `r20sub/` 那 14 张当成子界面数据用**——它们是无效数据，已在本文说明。

### 27.5 最要命的一处（本轮新发现）

```rust
wonderland_map_star_retries: 120,
wonderland_map_star_retry_ms: 2500,
```

`startup::EnterWonderland` 按 `M` 之后，靠**星标模板**在地图上找传送点，**重试 120 次、每次间隔 2.5 秒**
（最长 5 分钟）。

**但第 4 条转移（大世界 → 提瓦特地图）没有判据。** 也就是说：

- 如果 `M` 没生效（比如聊天框正开着，`M` 被打进了输入框），BOT **无法区分**"地图没开"和"开了但没找到星标"；
- 它只会**埋头重试 5 分钟**，然后把失败报成"找不到星标"，而不是"地图根本没打开"。

**⇒ 这是 BOT 流程里唯一一处"失败原因会被误导"的地方，优先级最高。**

### 27.6 本轮为第 4 条做判据的尝试与结论：**暂时做不出来，如实记录**

建模集用 `dist/ifacegrid` 的 `tv_map_1..4`（4 张提瓦特地图）。

**单变量全部重叠**（meanR/G/B、luma、dark、bright、brown、teal、darkteal、sat 各 4 vs 29 帧，无一分开）。

**区域描述子全部重叠**（顶部条、左上、左列、底部、右侧、整屏共 7 个区域，最好 0.87x）。

**二维组合**：`rough`(相邻像素平均绝对差，刻画地形纹理) + `dark` 在**建模集上零侵入**，
框为 `rough[14.44, 22.47] dark[0.020, 0.162]`。

**但独立验证失败**：

| 帧 | 实际是什么 | rough | dark | 在框内? |
|---|---|---|---|---|
| `map-screen.png` | **千星奇域地图**（不是提瓦特地图！）| 10.49 | 0.107 | ✗ |
| `map-via-M.png` | 同上类 | 10.54 | 0.089 | ✗ |
| `cold-to-qianxing-59/c01-map.jpg` | **真·提瓦特地图** | 17.10 | **0.000** | **✗** |
| `cold-to-qianxing-59/c02-map-fresh.jpg` | 同上 | 13.66 | 0.002 | ✗ |

而建模集里最近的非地图帧（`qxhall_59` / `f2panel_b` / `f2panel_c`）**只超出框 0.10**。

**⇒ 结论：那个"零侵入"是 4 个正样本撑起来的假象，框是过拟合的。**
**⇒ 按纪律不写入 app。**

### 27.7 顺带查出的两件事

**① 文件名再次不可信。** 我一直以为 `map-screen.png` / `map-via-M.png` 是提瓦特地图，
本轮看图才发现它们是**千星奇域地图**。这正是文档里早就写过的那条警告。
**⇒ 任何按文件名做的统计都必须先看图确认。**

**② 千星地图判据有覆盖盲区。** `map-screen.png` 是千星地图的**放大形态**（缩进到单个岛链），
app 对它判 `unknown`；判据只覆盖**总览形态**（`qxmap_a/b/c`）。
这一点此前没有记录过，**应补进第 15 节的局限里**。

### 27.9 落地：把第 4 条转移做成"可验证"（第 71 节实现）

**推论**：BOT 按 `M` **之前**正处于 `overworld`（`wait_for_paimon_menu` 刚确认过）。
地图一旦打开就会**盖住左上角 HUD**，世界判据随即失效。
所以 BOT **不需要**为提瓦特地图单独建判据，只要看**世界判据有没有由真变假**。

**实测验证**（`/debug/ui-state?image=`，第 71 节）：

| 帧 | 实际是什么 | kind | world 判据 |
|---|---|---|---|
| `cold-to-qianxing-59/c01-map.jpg` | **提瓦特地图** | `unknown` | `not_applicable` |
| `cold-to-qianxing-59/c02-map-fresh.jpg` | 提瓦特地图 | `unknown` | `not_applicable` |
| `sweep-49/02-map.jpg` | 提瓦特地图 | `unknown` | `not_applicable` |
| `map-screen.png` | **千星地图** | `unknown` | `not_applicable` |
| `map-via-M.png` | 千星地图 | `unknown` | `not_applicable` |
| `anchor-teyvat-56/t-00.jpg` | **真·大世界** | **`overworld`** | **`teyvat`** |
| `anchor-teyvat-56/t-10.jpg` | 真·大世界 | **`overworld`** | **`teyvat`** |
| `teyvat-regions-58/snow-01.jpg` | 真·大世界 | **`overworld`** | **`teyvat`** |

**⇒ 地图 5/5 全部不是 `overworld`；大世界 3/3 全部是 `overworld`。这条转移从此可验证。**

**代码改动**（`src/ui/routines/startup.rs`）：

```rust
press_key(Key::M)
wait_for_wonderland_map_open(context, config)?;   // <-- 新增
let map_star = wait_template_hit(...)?;           // 原来的星标重试
```

`wait_for_wonderland_map_open` 在 `wonderland_transition_timeout_ms` 内轮询，
要求**连续 `TEMPLATE_STABLE_HITS` 次**世界判据为假（避免过渡帧误判）；
超时则报**准确**的失败：`open_wonderland_map` /「地图没有打开（按键多半被输入框吃掉了）」，
而不是原来的 `locate_wonderland_map_star` /「找不到星标」。

**⇒ 效果**：`M` 没生效时**立刻**得到正确诊断，不再白等 5 分钟，也不再报错误的原因。

**顺带**：`src/ui/state.rs` 的 `world_is_teyvat` 开放为 `pub(crate)`（原来是模块私有），
这样例程层可以直接复用同一个判据，而不是各写一份。
